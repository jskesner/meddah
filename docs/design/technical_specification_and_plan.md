### 1.0 Module Registry, Capability Gating & Dormancy Architecture (`backend/app/ruleset_vm/module_registry.py`)

Meddah is a **universal ruleset interpreter**, not a game. Every subsystem in §1.2–§1.29 is therefore an **independent, optional module** that a user can enable, disable, or customize. The only non-optional code is the **Core** (Ruleset VM §1.1, event-sourced persistence, deterministic MUD parser, and the module registry itself). This section is the single source of truth for how modularity works; individual sections only describe *what a module does when active*.

#### 1. The `MeddahModule` Manifest
Every module ships a declarative manifest registered at startup:

| Field | Meaning |
| :--- | :--- |
| `module_id` | Stable identifier (e.g. `hit_locations`, `chase`, `law_justice`). |
| `spec_section` | The §1.x section that defines it. |
| `requires_primitives` | Ruleset building blocks the module needs in order to mean anything (e.g. `chase` needs a movement/contest resolution; `piety` needs a `HigherPowerBlock`). |
| `requires_modules` / `enhances_modules` | Hard dependencies vs. optional integrations (an `enhances` link degrades gracefully when the other module is off). |
| `provides` | Commands, UI panels, event hooks, schema blocks, and Studio editors the module contributes. All are hidden/unregistered when the module is not `active`. |
| `scope` | Where it can be toggled: `campaign`, `session`, or `player_local` (UI-only modules such as VFX or themes). |
| `ai_dependency` | Always `none` for core behaviour (Golden Rule #2); AI flair is a separate opt-in sub-toggle. |

#### 2. Three-State Resolution: `dormant` → `available` → `active`
1. **`dormant`**: The active ruleset supplies none of the module's `requires_primitives`. The module is **inert**: no commands, no UI, no prompts, no events, no AI context tokens, and zero CPU cost. *The engine never invents a mechanic to fill the gap* (Golden Rule #1 / Explicit Null Guarantee).
2. **`available`**: Required primitives exist but the host has not enabled the module. It appears only in the **Module Manager**.
3. **`active`**: Enabled by the Host/GM/Solo player (individually or through a *Module Profile*). Ruleset-declared primitives may *suggest* activation, but never force it.

> [!IMPORTANT]
> **Ruleset-defined ≠ engine-mandated.** If a ruleset defines a mechanic (hostile environments, crime, hit locations, piety, etc.), Meddah executes it faithfully *when the module is active*. A Host may still disable the module (an audited `MODULE_OVERRIDE` event records the choice so replay and rewind remain consistent). Nothing is ever "always on" except the Core.

#### 3. Disabling Is Graceful, Reversible, Permission-Gated & Disruption-Safe
* **Host-Controlled Module Toggling Permission (`can_toggle_campaign_modules`)**:
  - In Solo Play, the Solo Player is the Host and has full control over all module toggles.
  - In Multiplayer (Hosted Table or Persistent Guild Server), **Guest Players cannot toggle `campaign`- or `session`-scoped modules by default** (`can_toggle_campaign_modules: false` for `seat_role: player` and `spectator`; players may only adjust their own `player_local` client preferences such as local audio volume, local VFX/3D dice preferences within the Host's campaign visual policy, and accessibility settings).
  - The **Host (`is_server_admin / host`)** owns module-toggling authority and can selectively grant or revoke `can_toggle_campaign_modules` for **GM / Co-GM** seats.
* **Non-Disruptive Isolated Sandbox Test Instance (`[Test in Isolated Sandbox Instance]`)**:
  - To let the Host or authorized GM experiment with modules without disrupting an active multiplayer session, the **Module Manager** includes a **`[Test in Isolated Sandbox Instance]`** action that spins up a private, ephemeral Copy-on-Write clone of the current campaign snapshot in a local preview drawer (or pre-session staging window). The Host/GM can test-drive any module toggles or sub-options against sample rolls and encounters **with zero interruption or state mutation to the connected players in the live session**, and either discard the sandbox or stage the changes for the next safe boundary.
* **Safe-Boundary Live Activation & Automatic Checkpointing**:
  - Applying module changes to a live campaign requires an explicit Host/GM confirmation prompt (previewing any affected dependent modules), automatically writes a pre-change event-store checkpoint, and queues the audited `MODULE_OVERRIDE` event to activate at a **Safe Boundary**—defaulting to **`Next Scene / Rest / Session Boundary`** during an active multiplayer session (or **`End of Current Atomic Turn / Resolution Step`** when the Host/GM explicitly selects immediate turn-end activation), never aborting an in-flight dice roll or reaction window.
* **State is preserved, not deleted**: Module-owned state stays in the event log; disabling merely hides and freezes it, and re-enabling resumes it (replay hashes verify the round-trip). When toggling `hit_locations` or switching vitality topologies mid-campaign, current health percentages map proportionally between `vitality.total` and `vitality.locations[id]`.
* **Dependency validation**: Disabling a module with active dependents shows the exact fallback (e.g. turning off `hit_locations` makes armor revert to the ruleset's aggregate defense; turning off `law_justice` removes crime hooks but keeps settlements intact).
* **No orphaned UI**: Panels, Capabilities Deck tabs, action-bar buttons, Studio editors, and AI prompt fragments all unregister with their module.

#### 4. Module Profiles (Bundles of Toggles, Never Mechanics)
Profiles only flip module flags and sub-options; they contain no rules content:
* **Theater of the Mind / Minimal**: Core + AI/Deterministic GM + Capabilities Deck. Everything else off.
* **Classic Tabletop**: Minimal + tactical VTT, rest/downtime, loot, quests, companions.
* **Full Simulation**: Everything the ruleset has primitives for.
* **Custom**: Per-module checkboxes plus per-module sub-options. Users can save, share, and fork profiles (`.rpgprofile`), and apply them per campaign or per session.

#### 6. Modularity Rules for Authors of New Modules
1. A module **may not hardcode game terms, numbers, or outcomes**; values come from ruleset blocks or explicit user configuration (including defaults for *tone/pacing* settings, which are UX, not rules).
2. A module **may not import another module's internals**; it communicates through the Core event bus and declared `requires_modules`/`enhances_modules` (enforced by `import-linter` independence contracts, see the Development Workflow document).
3. Any "default" that changes *outcomes* (fudging, rescues, safety nets) must ship **off**, or be selected explicitly through a user-chosen profile or GM style preset.
4. Every module needs a **manifest**, a **dormancy test**, and an **on/off round-trip replay test** (Universal DoD item 8).

#### 7. Verification
* **Dormancy Conformance**: Loading `rules_light_narrative.rpgrules` (the zero-stat fixture) with *every* module installed must yield `dormant` for each module that needs absent primitives and expose only Core commands/UI.
* **Toggle Round-Trip**: For each module, `enable → play → disable → enable` yields an identical state hash to uninterrupted play.
* **`tools/lint_modularity.py`**: Fails CI if a module registers `provides` without a manifest, imports a sibling module, or contains a non-allowlisted game term.

## 2. Complete Phased Implementation Plan (14 Incremental Phases + Phase 2.5 Slice — All MVP Phases First)

When you grant explicit permission to begin development, we will execute the build across **14 focused, well-balanced, incrementally verifiable phases plus an early Phase 2.5 playable vertical slice**, organized into two contiguous tracks:
1. **Track A — Contiguous MVP Release (`Phases 1–6` + `Phase 2.5 Slice`)**: Every MVP phase comes numerically before any Post-MVP phase. Completing Phase 6 delivers the complete, end-to-end 1.0 MVP across Desktop, Unified Browser Web Client, and CLI in both `Tier A (Zero-AI)` and `Tier B/C (AI-Enabled)` modes.
2. **Track B — Well-Balanced Post-MVP Modular Expansions (`Phases 7–14`)**: Eight cohesive, evenly-sized expansion phases where every subsystem registers as an independent `MeddahModule` (§1.0) without mutating MVP core schemas.

> [!IMPORTANT]
> **Core Development Directive — 100% Deterministic / Zero-AI Usability**:
> The entire engine and every subsystem across all phases must be **100% usable and playable deterministically without AI (`Tier A / Zero-AI Mode`)**. Every AI-assisted workflow (ingestion, GM narration, companion autonomy, quests, world generation, map transposition, ruleset co-design, and media) must have a first-class deterministic counterpart (structured parsers, procedural/table-driven generators, deterministic heuristics, manual/visual editors, and procedural asset fallbacks). **Every phase includes a mandatory Deterministic / Non-AI Test Suite (`pytest -m zero_ai`)** executed with all AI providers hard-disabled to enforce this directive.

### Universal Phase Definition of Done (DoD)
To ensure system integrity and prevent architectural drift, **every phase** must fulfill these requirements before being marked complete:
1. **Mandatory Deterministic / Non-AI Test Suite (`pytest -m zero_ai`)**: Every feature, workflow, and UI view introduced in the phase is tested end-to-end with all LLM/AI providers disabled (`AI_PROVIDER=none`), asserting `0` AI calls and 100% deterministic usability.
2. **Automated Unit & Property Tests**: All new modules covered by `pytest` + Hypothesis property tests.
3. **Agnosticism & Core Protection Lint**: `0` hardcoded game terms (e.g., `HP`, `AC`, `d20`, `spell_slot`) in engine core or optional modules (`tools/lint_agnosticism.py`); post-MVP phases may only add new building blocks and extension interfaces without mutating MVP core schemas without a versioned migration.
4. **Module Boundary Conformance**: Passes `import-linter` verification of the strict unidirectional dependency hierarchy *and* the sibling-module independence contract.
5. **Performance & Determinism Checks**: Passes memory and response budgets; verifies seeded RNG replay determinism (`pure_event_apply`).
6. **Living Documentation, Roadmap & ADRs**: Updated `ROADMAP.md` (validated by `tools/roadmap.py`), `docs/adr/`, docstring-generated API/building-block reference pages, and `CHANGELOG.md` entry.
7. **Working Acceptance Demo Script**: An executable test script or interactive scenario demonstrating the phase's delivered capabilities (including in Zero-AI mode).
8. **Module Manifest, Dormancy & Toggle Round-Trip (§1.0)**: Every module introduced registers a `MeddahModule` manifest, passes the dormancy test against `rules_light_narrative.rpgrules`, and passes the `enable → play → disable → enable` replay-hash test (`tools/lint_modularity.py`). Outcome-altering defaults must ship off (Rules as Written).

## 2.1 Grill-Me Resolutions (Scope, Baselines & Early Playability)

1. **Early Thin Vertical Slice ("Phase 2.5" — Terminal CLI MUD & Headless Server Daemon)**: After Phases 1–2, build the interactive **Terminal CLI MUD Client (`meddah attach`)** and **Headless Server CLI (`meddah serve`)** so the 3 showcase rulesets, ingestion, and (later) the AI GM can be played, tested, and hosted from the terminal well before Phase 6. There is **no** separate "text-only browser" client—the single **Unified Browser Web Client** (which serves Spectators, Players, Co-GMs, and Headless Server Admins from one shared React web bundle) and the Electron Desktop App are built in Phase 6 [MVP] (with post-MVP studios and audiovisual spectacle in Phase 13).
2. **LLM Baseline**: Minimum supported tier is a mid-range local model (7–14B via Ollama, ~8–16GB VRAM). All deterministic paths must work with zero LLM calls; prompts and the 4k–8k budget are tuned for that tier; cloud models are an upgrade.
3. **Content & Licensing Posture**: Personal, non-commercial. No copyrighted content shipped; users supply their own rulebooks/modules; ingested data stays local. The 3 showcase rulesets use original or open-licensed (SRD/CC) content only.
4. **MVP Boundary & Contiguous Phase Ordering**: All MVP phases come numerically first (**Phases 1–6 plus the Phase 2.5 thin playable slice**): Phase 1 (Core Ruleset VM, Module Registry & MUD Parser), Phase 2 (Ruleset Ingestion & 14 Probes), Phase 2.5 (Terminal CLI MUD & Headless Server Slice), Phase 3 (Event-Sourced Persistence, Cosmology, Multi-Floor Dungeons & Chronology), Phase 4 (Deterministic & AI GM Director, Difficulty/Mercy & Quests), Phase 5 (Host-Authoritative Multiplayer, Split-Party, Safety & Media), and Phase 6 (Desktop Shell, Unified Browser Web Client, MUD Terminal, Core 2.5D VTT Canvas, Dynamic Character Sheet, 3-Mode Builder, 4-Tab Capabilities Deck & **Visual Ruleset Studio GUI**). All Post-MVP modular expansions follow in well-balanced contiguous order (**Phases 7–14**).

5. **Playable Test Criterion**: Phase 2.5 is deterministic-only (no AI GM yet; the AI GM arrives in Phase 4). The first AI GM acceptance test is one scripted scenario on the d20 fantasy showcase ruleset: a 30-minute session with no rules errors, no hallucinated mechanics, and every roll resolved by the VM.
6. **Agnosticism Enforcement**: A golden-file conformance suite (scripted scenarios, seeded RNG, expected event logs per showcase ruleset), a CI lint that fails on any game-term reference (HP, AC, d20, etc.) in engine-core code, and a 4th deliberately unusual fixture ruleset added in Phase 1 to expose hidden assumptions.

7. **AI/VM Consistency Contract**: The LLM may only propose structured tool calls (roll request, apply effect, move entity, spawn, etc.). The VM validates each against the ruleset schema and current state and commits it as an event. Invalid calls are rejected with an error and retried up to N times, then fall back to a deterministic or narrative-only response. Prose never changes state directly.
8. **Multiplayer Threat Model**: Host-authoritative with server-side validation. Guests send only intents, never state. The server filters fog-of-war, hidden rolls, and GM-only data before transmission, and Tunnel/Invite Codes require a per-session token. Trust model is friends-and-family (not hostile public play), but secrets are never sent to clients.

9. **LLM Latency & Failure Handling**: Non-blocking by design. Deterministic engine and MUD commands always respond instantly. Slow LLM calls stream tokens with a visible "GM is thinking" indicator and a configurable timeout (e.g. 60s). On timeout/failure the system offers Retry, Switch to Fallback Provider, or Continue with a deterministic stub. In multiplayer, other players' deterministic actions are never blocked by a pending LLM call.
10. **AI Content Provenance & Governance**: All AI-generated content (NPCs, rooms, items, quests, ingested blocks) is committed as an event tagged with provenance (model, prompt hash, timestamp) and lives in the Campaign Overlay, never touching the immutable base ruleset or world template. Ruleset-level content is always staged in the Diff Workbench. Players can inspect, edit, lock, or discard AI content; "Bake to Template" is always an explicit user action.

11. **Versioning & Save Compatibility**: Every `.rpgrules`/world/campaign file carries a `schema_version` and content hash. A campaign pins the exact ruleset version it started on; ruleset edits create a new version and the user chooses "Stay on pinned" or "Migrate" (with a diff and an automatic checkpoint first). Engine upgrades ship event-log migration scripts, so old saves open, or fail with a clear message, never silently corrupt.
12. **Media & Secrets Management (Desktop Keychain + Layered Headless Secret Resolver)**: Content-addressed local media cache in the campaign folder. Media is generated only when a provider is configured, with a per-session size/cost cap and a visible "generating" placeholder. On Desktop, provider API keys live in the OS keychain; on **Headless Linux / Docker** (where no desktop OS keyring exists), the **Layered Headless Secret Resolver** loads secrets in priority order from: (1) Docker Secrets / file-mounted paths (`*_FILE` env vars such as `/run/secrets/openai_api_key`), (2) standard environment variables (`.env` / `OPENAI_API_KEY`), or (3) an optional age/Fernet-encrypted `/data/config/secrets.enc` vault unlocked via `MEDDAH_MASTER_KEY`—and strictly never stores secrets in `.rpgcampaign` files or SQLite event logs. Campaign export bundles media optionally. The campaign works fully with no media providers.

13. **Export / Import Workflow**: Three portable, versioned, zip-based packages: `.rpgrules` (ruleset plus compendium), `.rpgworld` (world template with maps/tilesets, optionally bundled rules), and `.rpgcampaign` (event log, overlay, pinned ruleset, optional media). Every export shows a manifest with checksum and `schema_version`. Import runs through the Staging/Diff Workbench with conflict resolution. API keys/secrets are never included; a "player-safe" mode strips GM-only data; "Redact copyrighted compendium text" is on by default for ruleset exports. Implementation: backend in Phase 3 (storage) with Visual Ruleset & Package Studio UI in Phase 6 [MVP]; `.rpgcampaign` export/import is part of the MVP.

14. **Package File Format (`.rpgrules` / `.rpgworld`)**: Zip container with `manifest.json` at the root (`type`, `schema_version`, `engine_min_version`, content hash, dependency list with version hashes, license/attribution, and `redaction` flags). Hand-editable content is one YAML (default) or JSON file per building block under `blocks/`; large catalogs use JSONL; assets are content-addressed under `assets/<sha256>`. The compendium FTS/vector index is NOT shipped and is rebuilt on import. Validation uses published JSON Schemas generated from the Pydantic models so external tools and VCS diffs work.
15. **Campaign On-Disk Layout & Integrity**: A campaign is a folder: `campaign.sqlite` (append-only event log, checkpoints, overlay projections; WAL mode), `media/` (content-addressed cache), and `pins.json` (pinned ruleset/world versions + hashes). `.rpgcampaign` export is a zip of that folder after a SQLite checkpoint/vacuum. Projections are rebuildable from the event log; import verifies by replaying events and comparing a state hash, and repairs a corrupt projection instead of failing.

16. **Crash Safety, Autosave & Backups**: Every event commits to SQLite (WAL, fsync on commit) before being acknowledged, so a crash loses at most the in-flight action. Automatic checkpoints on scene change, rest, and every N minutes. Rolling backups of the campaign folder (default last 5, on session start/end) go to a separate configurable location. After an unclean shutdown the app offers Resume (replay from last checkpoint) or Restore from backup. Multiplayer guests reconnect by re-syncing from the host's state.
17. **Localization (i18n)**: Not in MVP, but designed in: all player-facing strings and engine messages live in ID-keyed string tables (no hardcoded English in code paths). Rulesets carry a language tag; the AI GM is told the table's preferred language; TTS voices are chosen per language; UI translation packs are a post-MVP hook.
18. **Extensibility Model**: Post-MVP, declarative-first. Content extensions (blocks, tilesets, themes, prompts, tables) are code-free packages. Behavioral extensions (custom LLM/image/TTS providers, importers) use a versioned Python provider interface, loaded only from a user-approved folder with a permissions manifest. The provider interfaces built in Phases 4 and 5 are written to this contract from the start.

19. **Packaging, Headless Server Installation, Docker & Updates**:
   - **Desktop App**: Linux-first, with Windows/macOS builds via CI once the MVP is stable. `electron-builder` (AppImage/deb, then NSIS/dmg) with the Python backend as a frozen sidecar.
   - **Optional Headless / Server-Only Installation (No Desktop GUI Required)**: The Python backend (`backend/`) can be installed standalone via `uv tool install ./backend` / `pipx` / `pip` (zero Electron or Node.js runtime needed), managed via the `meddah` CLI (`meddah serve`, `meddah campaign`, `meddah seat`, `meddah backup`, `meddah ruleset`), and accessed via CLI MUD (`meddah attach`) or the bundled static **Browser Light Client** (`--serve-web-client`).
   - **Official Headless Server Docker Image**: Multi-stage `docker/Dockerfile.server` and `docker/docker-compose.server.yml` packaging the Python server + static Browser Light Client assets (with non-root user, `/data` volume, healthcheck, and optional `ollama` service profile).
   - LLM/TTS/image models are never bundled; updates are manual download/pull plus a version-check notice; no silent auto-update in MVP.
20. **Performance Budgets (CI-tested)**: Deterministic command round-trip <5ms; state diff to clients <50ms; 60fps on a 100x100 tactical map with 50 tokens; 30fps on the multi-scale canvas; cold start <10s excluding LLM load; backend memory <1.5GB with no model loaded (LLM runs out-of-process); replay of 100k events <5s (checkpoints bound the typical case). Documented reference machine: 8-core CPU, 16GB RAM, 8GB-VRAM GPU.
21. **Onboarding / First-Run Wizard**: Skippable steps: (1) detect and test-ping local providers (Ollama, llama.cpp, ComfyUI, Kokoro/Piper); (2) recommend models by detected VRAM with one-click Ollama pull; (3) optional cloud API keys (keychain); (4) pick a showcase ruleset; (5) a 10-minute guided tutorial scenario (MUD commands, roll prompts, VTT toggle). Reopenable from Settings. "Play without AI" (zero-LLM mode) is a first-class choice.
22. **Telemetry & Logging**: No telemetry, analytics, or call-home, ever. Local structured JSONL logs (rotated, size-capped) with per-subsystem levels. A separate opt-in "AI Transcript" log (prompts/responses with provenance) is off by default because it may contain private content. "Export Diagnostics Bundle" collects redacted logs, versions, and hardware info, with a preview before saving. The only outbound traffic is user-configured providers and an optional manual version check.

23. **Accessibility Verification**: Automated + manual. CI runs axe-core and Playwright checks on key screens (contrast tokens, focus order, ARIA landmarks, reduced-motion); every theme preset must pass a contrast-ratio unit test; a manual checklist covers VTT grid readout and live-region narration with Orca (Linux) and NVDA/VoiceOver as platforms are added. Accessibility is a release gate. The claim is "WCAG 2.2 AA verified, AAA where feasible"; earlier unqualified "WCAG AAA" wording has been updated to this claim (the High-Contrast theme's >7:1 contrast target remains AAA-level).
24. **Hardware Capability Tiers (Unified 3-Tier Model)**: Detected at first run and re-checkable in Settings.
   - **`Tier A` (Zero-AI / 100% Deterministic)**: No LLM (`AI_PROVIDER=none`); complete deterministic play via `deterministic_gm_director.py`, `deterministic_dialogue_broker.py`, `improvised_stunt_resolver.py`, `canonical_deed_ledger.py`, and the Solo RPG Oracle.
   - **`Tier B` (Local LLM Reference Baseline — 7–14B via Ollama, ~8–16GB VRAM)**: **Our primary design target** for the full MVP AI experience, all 4k–8k token JIT Micro-Prompts, and the **Phase 2 & Phase 4 LLM evaluation gates**. Includes an automatic **`Tier B-Lite` (3–8B or CPU-only)** sub-profile that restricts AI to structured tasks with a 2–4k token budget and routes multi-NPC impulses and heavy ingestion to deterministic fallbacks.
   - **`Tier C` (Cloud / Frontier API or Large 30B–70B+ Local Models)**: Optional upgrade tier with expanded context and multi-agent polish; never required for any feature or phase gate.
   - The UI shows the active tier and per-feature availability instead of failing silently, and supports **bidirectional mid-campaign hot-swapping (`Tier A <-> Tier B <-> Tier C`)** without losing narrative continuity.

25. **Ingestion Accuracy Harness (Phase 2 Dual-Track Gate)**: A small corpus of open-licensed rulebooks (e.g. SRD 5.1, Cairn, Ironsworn, FATE Core, BRP SRD) with hand-authored gold `.rpgrules`. Evaluated on two tracks: **Track 1 (`Tier A` Deterministic Gate)** requires 100% pass rate on structured YAML/JSON/Markdown/CSV imports and deterministic regex/table probes with `AI_PROVIDER=none`; **Track 2 (`Tier B` Local 7–14B LLM Gate)** evaluates unstructured rulebook extraction on our reference 7–14B local model via Ollama (metrics: per-domain precision/recall of extracted blocks, formula-correctness on sampled rolls, and zero falsely invented domains, with $\ge 90\%$ core mechanics correctness).
26. **VM Expressiveness (Phase 1 exit criteria)**: Seven systems run on the same unmodified engine core, each with golden scenarios: d20 roll-over; d100 roll-under with degrees; 2d6 tiers + clocks; dice-pool-with-successes; step-dice or symbol-dice; bidding/resource-wager or card-draw (Fate Deck / momentum style); and a rules-light "no-stat" narrative fixture. Any engine-core change required is a design bug: extend the building-block vocabulary rather than special-casing.
27. **Scope Control**: Each phase has a Definition of Done: acceptance tests, perf budget check, agnosticism lint pass, docs, and a demo script. Post-MVP subsystems may only add building-block types and extension points, never modify MVP core schemas without a versioned migration. A subsystem starts only when its dependencies are green. A scope review at the end of each phase may cut or defer items.
28. **AI GM Evaluation (Phase 4 Dual-Track Gate)**: Evaluated on two tracks: **Track 1 (`Tier A` Deterministic Gate)** runs the 30-minute scripted d20 fantasy scenario end-to-end with `AI_PROVIDER=none` in every CI run; **Track 2 (`Tier B` Local 7–14B LLM Gate)** runs the same scripted scenario (seeded dice, pinned **7–14B local model via Ollama**) scored on rules fidelity (deterministic: `0` illegal tool calls, `0` state contradictions), narrative coherence/tone (1–5 rubric), pacing, and hint/mercy behavior. Both the AI GM under test and the rubric evaluator run locally on `Tier B` (`Ollama` 7–14B) by default (with an optional dev-only override if a developer ever wants to compare against another model). Real-LLM evals run on demand and at Phase 2 / Phase 4 gates (see item 31), never on a recurring CI schedule.
29. **Long-Campaign Memory & Structured Canonical Deed Ledger**: (1) Canonical facts (names, relationships, quest state, inventory, faction standing) plus the **Structured Canonical Deed Ledger (`canonical_deed_ledger.py` `DeedFact` records)** live as structured event-store state, never summarized away, and are queried deterministically by ID/tags so `Tier A (Zero-AI Mode)` NPCs, companions, and chronicles remember past deeds across 50+ sessions with `0` LLM calls—and so campaigns can hot-swap freely between `Tier A` and `Tier B/C`. (2) Episodic scene summaries written at scene end with importance scores and decay (LLM-summarized in `Tier B/C` or deterministic digest in `Tier A`). (3) Rolling hierarchical summary (scene → session → arc) keeps the 4k–8k `Tier B` prompt bounded. (4) Facts the LLM asserts that conflict with canonical state are rejected by the tool-call validator. (5) A "Campaign Memory" viewer lets players pin, edit, or delete memories. Prompt budgets per section are fixed (starting point: 40% scene, 25% canonical facts & deeds, 20% memory, 15% rules), tuned for `Tier B` (4k–8k context).
30. **Layered Content-Safety Pipeline**: (1) Lines/Veils and content rating are injected into every system prompt. (2) A fast deterministic keyword/pattern filter plus an optional lightweight classifier checks output before display; on a hit, regenerate once, then replace with a fade-to-black veil. (3) Provider refusals are caught, retried with a rephrased scene prompt, then fall back to a neutral narrative stub, never an error dump. (4) The X-Card always works instantly and rewinds the last beat. (5) Image and TTS prompts share the same filter. Filter hits are logged locally only.
31. **Testing Strategy**: Unit and property-based tests (Hypothesis) for the VM, dice, AST evaluator, and parsers, plus a malformed-ruleset fuzzer; golden-file scenario tests; event-store tests (replay determinism, migration, crash injection); a multiplayer integration harness with scripted headless clients (latency, disconnects, concurrent actions); a scripted mock LLM provider for deterministic CI; UI component tests, Playwright E2E against the Electron app, and visual-regression snapshots for the VTT canvas. Coverage is tracked per subsystem, with the VM core held to a higher bar. **Real-LLM evals are NOT run on a schedule** (hobby-project scope): they run only when a phase gate requires them (Phase 2 ingestion harness, Phase 4 AI GM acceptance scenario) or when manually triggered after prompt/model changes.
32. **Multiplayer Concurrency Model**: One serialized command queue per scene (actor lock), with the event log as sole source of truth. Different scenes (split parties) run in parallel; within a scene, actions process in arrival order. Reaction windows are sub-states of the pending action, and timeouts auto-resolve per the ruleset or host setting. Real-time/freeform mode batches near-simultaneous intents within a short window (~150ms) and orders them deterministically. LLM calls are async and never hold the scene lock: they propose tool calls that re-enter the queue and are re-validated against current state; stale proposals are rejected and the GM re-plans.

33. **Repository Layout & Module Boundaries**: Monorepo: `backend/` (Python, src layout, `uv` workspace), `desktop/` (TypeScript, pnpm), `sample_rulesets/`, `schemas/` (generated JSON Schemas), `docs/` (incl. `docs/adr/`), `tools/`. Strict one-way backend dependency order enforced by import-linter in CI: `ruleset_vm` depends on nothing in the app; `storage`, `world_gen`, `systems`, `ingestion` depend on `ruleset_vm`; `agents` depends on those; `multiplayer` and `media` sit above; the API layer is on top. TypeScript wire types and JSON Schemas are generated from the Pydantic models by one script; CI fails if generated files are stale.
34. **Architecture Decision Records**: Decisions become lightweight ADRs in `docs/adr/` (`NNNN-title.md`: context, decision, consequences, status). The 46 decisions plus Section 2.1 seed the initial set; the two spec files remain the narrative overview. Changing a decision means a new superseding ADR, never a silent edit. Phase Definition of Done includes "ADRs updated".
35. **Wire Protocol Versioning & Handshake**: Each WebSocket session starts with a handshake exchanging `protocol_version` (major.minor), engine version, and ruleset/world hashes. Major mismatch is refused with a clear "please update" message; minor mismatch is allowed (additive changes, unknown fields ignored). Typed JSON-RPC envelopes with schemas generated from Pydantic. Guests must hold the host's pinned ruleset hash; the host streams the package on join if missing, after guest approval. Hosts send only role-visible state.
36. **Toolchain & CI Gates**: Python 3.12+, `uv` (lockfile), `ruff`, `pyright` (strict on `ruleset_vm`, standard elsewhere), `pytest` + Hypothesis. TypeScript strict, pnpm, ESLint, Prettier, Vitest, Playwright. Pre-commit runs fast checks. Required CI gates: lint, type-check, unit tests, import-linter, agnosticism lint, schema-staleness check, perf-budget tests. No scheduled nightly jobs (hobby scope); slower jobs run on demand or at release.
37. **Dependency, License & Asset Hygiene**: Lockfiles for both ecosystems; grouped monthly update PRs (Dependabot/Renovate-style); `pip-audit` and `pnpm audit` plus a license checker with an allowlist (MIT/BSD/Apache/MPL/ISC; GPL/AGPL/unknown require an ADR). Project license MIT or Apache-2.0 (chosen at repo creation). `THIRD_PARTY_NOTICES.md` generated from lockfiles; `assets/PROVENANCE.md` records source and license of every bundled asset, sample ruleset, font, and sound. Model weights are never bundled.
38. **Determinism Rules**: Hard rule inside `ruleset_vm` and event-apply code. (1) All randomness from named, seeded RNG streams per scene (`dice`, `loot`, `encounters`, ...); each roll's stream position is recorded in its event. (2) No wall-clock, system RNG, or unordered-set iteration there (time comes from the in-world clock/events). (3) Event application is a pure function of (state, event). (4) AI output is recorded as events and never regenerated on replay. (5) A replay-determinism test replays every golden campaign and asserts identical state hashes; a lint forbids `random`, `time.time`, and `datetime.now` in those packages.
39. **Error Taxonomy & Validation UX**: (1) Author errors (ruleset/world/package) carry a stable code, file/block path, line/column where available, plain-language message, and suggested fix; shown in the Studio problems panel and CLI. (2) User-facing runtime errors are friendly, localized by string ID, never show stack traces. (3) Engine bugs (invariant violations) are caught at the scene-queue boundary, logged with a correlation ID, roll the scene back to the last consistent event, and offer "Export Diagnostics". Stable codes (`RPG-E####`) documented in `docs/errors.md`. `meddah validate <package>` CLI runs the same validator as the app.
40. **Branching, Commits & Releases**: Trunk-based development on `main` with short-lived branches and small PRs (self-review checklist for solo work; CI must be green). Conventional Commits enforced by a commit-msg hook. SemVer with `0.x` until formats stabilize. Package formats and the wire protocol are versioned and migrated from the first tagged release; internal Python APIs are unstable until 1.0. `CHANGELOG.md` generated at each tag. Each phase ends with a tagged milestone release (`v0.N`) and a demo script.
41. **Documentation as a Deliverable**: Docs are part of Definition of Done. Required: `docs/ruleset-authoring.md` (building-block reference partly generated from JSON Schemas, with annotated showcase examples), `docs/quickstart.md`, `docs/architecture.md`, `docs/errors.md`, `docs/adr/`, `CONTRIBUTING.md`. Each building-block type has a docstring-derived reference page so docs can't drift. In-app help links to the same docs; the tutorial scenario doubles as living documentation.
42. **Spikes (on-failure only)**: Decision: NO planned up-front spikes. Risky areas (PDF extraction quality, PixiJS multi-scale canvas performance, sidecar packaging, tunnel approach, local-model structured-output reliability) are tackled directly in their phases; a time-boxed spike with a written go/no-go ADR is run only if an implementation attempt fails or misses its budget. Spike code lives outside `backend/` and `desktop/`.
43. **Untrusted-Input Security**: (1) Formula/AST evaluation uses a custom parser with no `eval`/`exec`, a function whitelist, and hard limits on depth, node count, loop iterations, and wall-time. (2) Package import rejects path traversal (zip-slip), absolute paths, symlinks, and zip bombs (entry count, per-file and total uncompressed size, compression-ratio cap) and validates manifest/schema before extracting. (3) URL ingestion blocks private/loopback addresses (SSRF) and limits redirects, response size, and content types, with an optional domain allowlist. (4) PDF/HTML parsing runs in a subprocess with size/time limits. (5) Extension providers and WebSocket messages are schema-validated with size and rate limits. (6) Ruleset and AI text is escaped before rendering; the Electron renderer uses `contextIsolation` on, `nodeIntegration` off, and a strict CSP.

44. **Manual Roll / Sheet-Override Play Modes**: There is NO formal manual dice-entry feature in the engine. Instead, solo players and GMs/hosts may (a) set the engine to NOT resolve player-facing rolls (background RNG for world systems may still run), and (b) grant players permission to directly edit their character sheets and status (HP, mana, etc.), effectively bypassing the deterministic rules. Direct edits are committed as audited `SHEET_OVERRIDE` events so replay and timeline rewind stay consistent.
45. **Multiplayer Connection Tiers (no public server required)**: The host's backend serves the browser guest client itself. (1) LAN/direct: guests open `https://host-ip:port` (self-signed or locally trusted cert, with clear instructions). (2) One-click tunnel (e.g. Cloudflare Tunnel) provides valid public HTTPS with no port forwarding. (3) VPN overlays (Tailscale/ZeroTier) are documented, not built in. (4) WebRTC peer-to-peer is post-MVP. The invite is a short code plus a link carrying a per-session token; a host waiting room approves each guest; the Electron client can join by the same link.
46. **Unified Browser Guest / Light Client (Spectator, Player, Co-GM, Host-as-Player & Host-as-GM Modes)**: One single lightweight web build target of the shared React components: MUD terminal, character sheet, capabilities deck, roll/reaction prompts, handouts, journal, and a read-only or lightweight VTT view. Capabilities unlock along two orthogonal axes: **(A) In-Game Seat Role (`spectator | player | host_player | co_gm | gm`)** and **(B) Server Admin Privilege (`is_server_admin: bool`, via `MEDDAH_ADMIN_TOKEN` or Host link)**. When a Host/Admin wants to **play as a Player Character in a multiplayer game while the AI GM (`Tier B/C`) or Deterministic GM Director / Solo Oracle (`Tier A`) runs the game**, they select **`Host-as-Player` Mode (`seat_role: "host_player"`)**: the server keeps the **Server & Session Admin Drawer** and **Shared Solo Oracle Drawer** unlocked for them while enforcing **strict Player-Level Fog-of-War & Spoiler Shielding** (hiding unrevealed map areas, secret doors, trap icons, and hidden NPC plots, and locking the Live GM Dock behind a spoiler confirmation guard). Conversely, selecting **`Host-as-GM` Mode (`seat_role: "gm"`)** unlocks both the Server Admin Drawer and the omniscient Live GM Dock. Heavy authoring Studios (Visual Ruleset Studio, Map/Tileset Import Studio, World Builder) stay in the Electron Desktop App—which can either run its own local sidecar OR connect directly to a remote Headless Server (`https://...` + `MEDDAH_ADMIN_TOKEN`) as a remote Studio workstation. Served by the host backend as static files (no separate web server needed). **Mobile phone support is explicitly off the roadmap for now.**
47. **Guest Identity & Seats**: Per-seat invite links persisted in the browser (localStorage token) let guests rejoin the same seat after refresh or disconnect, with no account. The host may optionally "remember" a guest and bind a seat to a stored device token across sessions. Invites expire (default 24h or on session end), can be revoked, and can be single-use or multi-use. Roles are per seat: `Player`, `Host-as-Player` (admin controls + player spoiler-shielding for AI-GMed / Solo-Oracle co-op), `Spectator`, `Co-GM`, and `Host-as-GM`. The host can kick or ban a device token. No central identity service exists.
48. **Session Lifecycle**: `Setup → Active → Wrapping Up → Ended` (plus `Interrupted` after a crash). The host/GM can end a session manually at any time. The pacing director may only SUGGEST ending (a non-blocking "good stopping point?" prompt at a scene boundary, a configurable soft time limit, or after a cliffhanger) and never ends a session itself; solo players get the same suggestion. "Wrapping Up" finishes the current scene, takes a final checkpoint, and awards XP/milestones before the end-of-session pipeline runs. A host-configurable idle timeout prompts before auto-ending. After a crash, the next launch offers to resume or end the interrupted session.
49. **End-of-Session Pipeline & Reports**: Triggered by the transition to `Ended`; ordered, idempotent steps with a visible progress panel: (1) final checkpoint and backup; (2) deterministic mechanical summary from events (XP, loot, quest changes, deaths, rolls, time passed) with no LLM; (3) episodic/hierarchical memory consolidation; (4) optional AI narrative recap and "Previously On..." text (skipped in Tier A); (5) per-player and GM reports; (6) export to a `reports/` folder in the campaign. Reports: Session Summary in Markdown, HTML, and PDF (rendered via Chromium print in the Electron app, or via the built-in lightweight pure-Python PDF renderer `WeasyPrint` / `ReportLab` / `fpdf2` in Headless Server / Docker mode so zero headless-browser bloat is required), with a player-safe version (no GM-only secrets) and a GM version. Steps can fail or be skipped independently, and reports can be regenerated later from the event log.
50. **Handout Library**: Campaign-scoped. The host imports images (PNG/JPG/WebP/SVG), PDFs (rendered per page), and text/Markdown via drag-and-drop, file picker, or paste, or extracts them from an ingested module. Files are validated (type sniffing, size cap, decompression-bomb limits, EXIF stripped) and stored content-addressed under `media/handouts/` with metadata (title, tags, folder, GM notes, source, license note). Visibility: Hidden, Shared with all, or Shared with selected seats; the host can "Show to players" as a pop-up or pin it in a Handouts drawer. Revealed handouts persist in the player's journal. Visibility changes are replayable events and the server only sends bytes to authorized seats. Handouts can attach to rooms, NPCs, or quests to surface automatically. Handout export is NOT supported (they come from external sources).
51. **Printable Character Sheets**: Each ruleset's sheet layout schema also defines a print template, rendered to HTML and exported to PDF via Chromium print in Electron, via the built-in pure-Python HTML-to-PDF renderer (`WeasyPrint` / `ReportLab` / `fpdf2`) on a Headless Server / Docker container, or via client-side `@media print` in the Browser Light Client. Variants: Blank (for pen-and-paper), Filled (current state), Compact/Full. Print-friendly high-contrast, ink-saving styling; tagged PDF where feasible. Also exportable: character JSON templates and companion/retinue cards. Rulesets without a print template get an auto-generated generic layout.
52. **Prompt Management**: Prompts are versioned template files under `backend/app/agents/prompts/` (one per task), each with front-matter: `id`, `version`, typed variables schema, token-budget section weights, required output schema, and optional per-model-family overrides. CI fails on missing variables or budget overflow. Prompt hash/version are recorded in AI event provenance. Users can override any prompt via a user prompts folder, shown in a Prompt Library panel with diff against the default and a reset button. Eval suites run against a pinned prompt version, and a prompt change requires an eval result note in the PR.
53. **Cloud Usage Ledger**: Each provider call records provider, model, task id, prompt/completion/cached tokens, latency, and an estimated cost from a user-editable price table (per 1M tokens; per image; per 1k TTS characters) shipped with defaults and a "prices may be stale" note. Local providers record tokens/time with cost 0. The ledger lives in the campaign database SEPARATE from the game event stream (so it never affects replay or determinism). A Usage panel aggregates by session, campaign, provider, and task. Provider-reported counts are preferred, with a local tokenizer estimate as fallback.
54. **Cost Controls**: Optional per-session, per-campaign, and per-day budget caps per provider category (LLM, image, TTS). At 80% a non-blocking warning appears. At 100% a user policy applies: "Warn and continue" (default), "Pause cloud calls and fall back to local/deterministic tier", or "Ask me each time". Pre-call estimates with a confirm step above a threshold for expensive calls (image generation, large PDF ingestion). The host's budget governs multiplayer spend; guests never use the host's keys directly because all calls go through the host backend. Everything stays local.
55. **Spectator Mode**: A read-only seat role. The host chooses the audience view: Public (shared MUD log, public map state, shared handouts, public dice results) or Party (adds one chosen party's perspective and fog-of-war). Never GM-only data, hidden rolls, secrets, other split parties' private scenes, or character sheets (unless the host enables sheets). Optional configurable delay (e.g. 0–120s) for streaming without spoilers. **No spectator chat.** Joined via a spectator invite link, subject to a host-set cap, using the browser client in read-only mode. Filtering is server-side with the same role-based view filter as players.

It lists all phases (14 + 2.5, with contiguous MVP Phases 1–6 + 2.5 and Post-MVP Phases 7–14), each with status (`Planned / In Progress / Done / Deferred`), MVP flag, deliverables checklist, and links to ADRs and spec sections, plus a "Deferred / Ideas" section. A machine-readable front-matter table is validated in CI by `tools/roadmap.py` (valid statuses, every Done phase has a tag and DoD checkbox, links resolve). GitHub Issues are used ONLY for bugs and user-reported problems (bug template, plus a lightweight feature-suggestion template that the maintainer triages into the roadmap file); issues may reference roadmap IDs but never replace them.
57. **Sample Ruleset Sourcing**: Derive where it helps, original where it doesn't. The d20 fantasy and 2d6 narrative rulesets are adapted from open-licensed SRDs (e.g. SRD 5.1 under CC-BY 4.0, and an open PbtA-style SRD) with attribution, also providing realistic gold data for the Phase 2 ingestion harness. 58. **Core Development Directive — 100% Deterministic / Zero-AI Usability & Per-Phase Non-AI Testing**: The entire engine across all 14 phases (plus Phase 2.5) must be 100% usable, playable, and feature-complete deterministically with zero AI/LLM providers enabled (`Tier A / Play without AI`). Every AI-assisted capability (ingestion, GM narration, solo play, companion autonomy, quests, world generation, map transposition, ruleset co-design, and media) must provide a complete deterministic counterpart (structured importers/parsers, Solo RPG Oracles & tables, template narration, tactical utility heuristics, visual/manual Studios, and procedural SVG/local audio fallbacks). Every phase must include a dedicated deterministic / non-AI test suite (`pytest -m zero_ai --disable-ai-providers` and E2E `Tier A` tests) in CI to enforce that no feature depends on an LLM to function.
59. **`Tier B` (7–14B Local LLM via Ollama, 8–16GB VRAM) Architecture & Evaluation Guardrails**:
   - **Pinned Reference Model Family**: Pin a primary open-weights reference family (e.g., `Qwen 2.5 / Qwen 3 7B–14B` via Ollama) as the golden Phase 2 / Phase 4 benchmark, plus smoke-test 1 secondary family (`Llama 3.1 / 3.2 8B`) to prevent prompt overfitting, keeping the model tag configurable in `.env` / `pyproject.toml`.
   - **Dual-Mode Grammar-Constrained JSON + Streaming Narrator Split**: Use Ollama's native grammar-constrained JSON Schema (`format: <json_schema>`) for mechanical tool proposals so syntax errors are impossible, paired with a lightweight streaming prose pass (or a `<narration> + <tool_calls_json>` envelope with a tolerant JSON repair parser for models without native grammar support).
   - **Hybrid Phase 6 Evaluation Scoring**: 100% deterministic checks for rules/mechanics fidelity (tool-call validity, state consistency, clue coverage, latency/token budget) + an independent secondary `Tier B` local judge model (with a strict 1–5 evidence rubric) for narrative coherence/tone + human playtest sign-off checklist.
   - **Zero-VRAM Default Retrieval in `Tier B`**: Default strictly to **SQLite FTS5 BM25 + entity/tag/rule-ID lookup** in both `Tier A` and `Tier B` (requiring `0` extra VRAM or embedding models), with local vector embeddings (`nomic-embed-text` / `ChromaDB`) as an optional opt-in enhancement.
   - **Deterministic-First Phase 2 Ingestion Pipeline**: Run the `Tier A` deterministic structural heading/table/stat-block parser FIRST to extract structured tables and isolate targeted 1k–2k token text chunks, then pass only those targeted chunks through Domain-Specific `Tier B` Micro-Probes using grammar-constrained JSON schemas with per-probe checkpointing.
   - **Zero-Bottleneck Companion Execution**: Active combat uses the `<1ms` Deterministic Tactical Utility Evaluator for all companion mechanical turns/rolls + disposition bark templates, invoking a single coalesced `Tier B` micro-prompt only on high-drama narrative beats or direct conversation.
   - **Zero-Stall Scene Memory & JIT World Expansion**: Scene transitions immediately commit a `<5ms` deterministic `DeedFact`/event digest and expand stub rooms deterministically via `procedural_jit_expander.py` (`<5ms`), running `Tier B` episodic summarization or prose polish asynchronously in the background when the GPU queue is idle; `Tier A -> Tier B` hot-swaps read directly from the `DeedFact` ledger.
   - **Single-GPU Resource Coordinator (`gpu_resource_coordinator.py`) & Priority Local LLM Queue (`local_llm_queue.py`)**: On 8–16GB GPUs, default images to Procedural SVGs and TTS to lightweight CPU/low-VRAM `Piper`/`Kokoro` (`~100–300MB`) so the 7–14B LLM stays hot in VRAM (sequencing optional ComfyUI in `"On-Demand Portrait / Map Only"` mode); coalesce near-simultaneous scene actions (`~150ms`) into one prompt and schedule split-party/background calls via a priority queue with a 1-click `[Resolve Deterministically Now]` bypass.
   - **Scoped Block-Slice Prompting in Ruleset Studio**: Send only the 3–8 referenced blocks + a ~500-token Ruleset Signature Header and require a grammar-constrained JSON Patch validated by the deterministic Schema Linter & Monte Carlo Simulator.

61. **MUD Communication DSL, Diegetic Channels & Post-MVP Front-End Visual FX / Graphical Randomizer Guardrails**:
   - **Multiplayer 3D Dice & Card-Draw Synchronization**: Public rolls and card draws animate identically on every opted-in player's screen using the server-broadcast `physics_throw_seed`; GM-Screen or Secret/Blind checks (*Stealth, Perception, Hole Cards*) animate face-up only for the authorized seat(s) while optionally displaying a mystery `"GM is rolling..."` shadow die or face-down card back (`[🂠]`) to other seats.
   - **Priority Cross-Fading for Simultaneous Condition Shaders (No Slot Mixing)**: When an entity has multiple active conditions with `ConditionVisualSpec` shaders, the `PortraitCompositor` and `TokenRenderer` never mix shader slots across different conditions at the same instant—instead, they render each condition's complete, cohesive shader package and **smoothly priority-cross-fade** across active conditions (weighted by severity/priority), while **all** active conditions continuously display their mini-icon badges along the portrait bezel and token ring.
   - **Multi-Scope Named Card Decks (`DeckBlock`)**: Rulesets can define any number of named `DeckBlock` instances scoped to `table_shared` (central Fate/Action/Initiative/Tarot deck), `per_entity` (personal player/enemy modifier or ability decks), or `encounter_local`, with a Deck Selector Pill in `CardDeckVisualizer.tsx`.
   - **Linked Portrait $\leftrightarrow$ VTT Map Token Synchronization**: Framed Ring and 2.5D Standee tokens dynamically mirror the portrait's active Vitality state (`Healthy -> Bloodied -> Critical -> Dead`), paper-doll gear updates, and priority cross-faded `ConditionVisualSpec` shader by default, with an optional per-entity custom top-down/standee sprite override.
   - **Non-Interrupting `whisper` Eavesdropping**: Whispers show a non-spoiler observer emote (`"Kale leans in and whispers quietly to Vane"`) and silently check against bystanders' Passive Perception/Observation (or roll a silent background check if an entity has actively toggled `> eavesdrop @target` or has a keen-hearing trait), leaking partial/full text only on a pass without interrupting chat flow with popup roll prompts.
   - **Three-Tier Channel & Frequency Alias Registry (`ChannelPresetRegistry`)**: Supports **(1) World/Ruleset Canonical Presets** (`#party-tac`, `#local-news`), **(2) Shared Party Presets**, and **(3) Personal Comms Contacts**—allowing players to bookmark any discovered or intercepted frequency during play (`> radio save syndicate-net 88.45MHz --party`) into campaign state, autocomplete, and the Comms HUD.
   - **Diegetic Medium Physical Room Audibility (`audibility_mode`), Condition Gating (`Silence`/`Paralysis`/`Deafened`), Sealed-Helmet / Vacuum Physics & Fine-Grained PA Voice Modulation**: Each `CommunicationMediumBlock` declares `audibility_mode` (`"audible_speech" | "subvocal_whisper" | "silent_mental_or_text"`) plus input modality gates (`requires_vocal_speech`, `requires_somatic_input`, `requires_mental_action`). Vocal-blocking conditions (`#muted`, `#gagged`, `#silenced`) block `say` and voice radios while still permitting somatic text terminals, visual `sign` language, or telepathy; `#paralyzed`/`#petrified` blocks both vocal and somatic channels while still permitting pure mental/telepathic links (`requires_mental_action: true`). Wearing a **Sealed Space-Suit / Diving Helmet (`#sealed_helmet`)** isolates voice inside the helmet so suit radio transmissions have `0` external room bleed (unless the external PA speaker is toggled on). When the external PA speaker is used, any metallic/vocoder filter is **100% optional** (defaulting to `clean_natural`), and rulesets/gear with `VoiceModulatorProfile` grant **fine-grained player control** over PA projection (`whisper_amp`, `normal`, `loud_hailer`, `booming_resonance`) and vocal timbre/masking (`clean_natural`, `metallic_vocoder`, `deep_dreadnought`, `scrambled_anonymous`, or `voice_mimic:@target`). **`#vacuum`** blocks open-air sound completely while supporting suit radios, visual `sign`s, and conductive `touch-helmet @target` speech.
   - **Ruleset-Grounded Diegetic Languages, Dialects, Written Scripts & Secret Cants (`LanguageBlock`)**: Supports inline (`> say in elvish "..."`) and Comms-Bar language selection across all spoken and written channels (including radios, broadcasts, telepathy, and couriers) with per-seat server-side fluency filtering (**Fluent / Translator** $\rightarrow$ full text; **Partial Fluency / Related Dialect** $\rightarrow$ root words + masked syllables; **Non-Speaker** $\rightarrow$ deterministic phonetic cipher or non-spoiler tag, with raw plaintext stripped from the wire), plus dual-layer **Secret Cants** (*Thieves' Cant / Druidic*) and `language_dependent` vs. `universal_conceptual` telepathy modes.
   - **Semantic Social Valence Tagging (`Tier A` & `Tier B/C`)**: All 60+ social emotes and vocal `(tone)` modifiers carry structured semantic valence tags (`respectful_greeting`, `hostile_intimidation`, `affectionate_comfort`, `sarcastic_taunt`) that deterministically shift NPC disposition/templates in `Tier A` (`deterministic_dialogue_broker.py`) and feed the NPC/Companion micro-prompt, TTS prosody, and portrait expression state swaps in `Tier B/C`.
